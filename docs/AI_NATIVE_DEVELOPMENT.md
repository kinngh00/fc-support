# AI-Native 개발과 검증 기록

## AI를 사용한 방식

이 프로젝트에서 AI는 코드를 대신 작성하는 단일 도구가 아니라 다음 과정을 반복하는 협업 파트너로 사용했습니다.

```text
실제 문제 정의 → 네트워크 응답 관찰 → 가설 수립 → 작은 구현
→ 실제 DB·API·화면 검증 → 오류 원인 수정 → 자동 테스트로 고정
```

제품 기준과 최종 결정은 사람이 정하고, AI가 제안한 구현은 실제 응답과 실행 결과로 검증했습니다. API가 제공하지 않는 값은 추정값으로 채우지 않는 것을 프로젝트의 기본 원칙으로 삼았습니다.

## 주요 의사결정

### 1. 매 검색마다 외부 API를 호출하지 않는다

- 문제: 사용자 요청마다 10,000명 데이터를 다시 조회하면 지연과 API 한도가 발생합니다.
- 결정: 매시 05분에 백엔드가 수집하고 사용자는 SQLite의 활성 스냅샷만 조회합니다.
- 검증: 활성 스냅샷이 오래됐을 때 자동 재수집하는 신선도 테스트를 추가했습니다.

### 2. 수집 시작과 공개 시점을 분리한다

- 문제: 새 데이터와 이전 데이터가 섞이거나 수집 중 장애로 일부 데이터만 공개될 수 있습니다.
- 결정: `building → active → retained` 상태 전환과 원자적 승격을 사용합니다.
- 검증: 완료 전에는 기존 활성 스냅샷이 유지되고, 중단된 수집은 실패 처리하도록 구현했습니다.

### 3. 포메이션은 랭킹 문자열이 아니라 최근 매치의 포지션으로 계산한다

- 문제: 매치 상세는 좌표나 완성된 포메이션명을 주지 않고 선수 포지션 코드만 제공합니다.
- 결정: GK를 제외하고 수비, 수비형 미드필더, 중앙 미드필더, 공격형 미드필더, 공격수 그룹 인원수를 세어 포메이션을 계산합니다.
- 검증: 실제 JJC제주 최근 매치 포지션으로 `4-1-2-3`이 계산되는 테스트를 고정했습니다.

### 4. 선수 정보는 SPID를 메타데이터와 결합한다

- 문제: 매치 응답에는 SPID와 포지션 숫자 중심으로 제공되어 이름·시즌을 바로 알 수 없습니다.
- 결정: `spid.json`, `seasonid.json`, `spposition.json`을 결합합니다.
- 검증: SPID가 시즌 3자리와 PID 6자리로 구성됨을 실제 메타데이터로 대조했습니다.

### 5. 이미지 경로는 실제 FC 온라인 응답을 기준으로 수정한다

- 문제: 단순 SPID 이미지 URL은 403 또는 다른 이미지가 나오는 사례가 있었습니다.
- 결정: 공식 페이지가 반환하는 PID 기반 고해상도 경로와 액션 이미지 fallback을 실제 응답으로 확인했습니다.
- 검증: 특정 선수의 브라우저 네트워크 응답과 표시 이미지를 반복 비교했습니다.

### 6. AI의 변경 범위를 코드로 제한한다

- 문제: 요청하지 않은 UI 변경이 주변 요소에 영향을 줄 수 있었습니다.
- 결정: 작업 전 원자 요구사항, 허용 파일, 허용 영역과 변경-요구사항 연결을 로컬 범위 파일에 기록합니다.
- 검증: `npm run verify:scope`가 범위 밖 파일, 미검증 요구사항, 화면 검증 누락을 차단합니다.

## 실제 오류를 막은 사례

| 발견한 문제 | 검증 방법 | 재발 방지 |
|---|---|---|
| 매치 상세만으로 선수 이름·시즌을 알 수 있다고 잘못 판단 | 원본 JSON 필드 전체 확인 | 공식 메타데이터 결합 경로 사용 |
| 가격 그래프의 현재가와 마지막 기록 값을 혼동 | 원본 응답 배열의 의미 대조 | 마지막 기록을 선택하는 단위 테스트 |
| 포메이션 ON/OFF에서 서로 다른 스쿼드 표시 | 동일 최신 매치 ID와 선발 목록 비교 | 하나의 최신 매치 소스를 공통 사용 |
| 모바일 포메이션 카드 잘림 | 코덱스 내 390px 화면 캡처 | 데스크톱·모바일 시각 검증을 배포 조건화 |
| 댓글 작성 후 목록 댓글 수가 즉시 갱신되지 않음 | 실제 회원가입·게시글·댓글 UI 흐름 실행 | 상세 응답을 목록 상태에도 동기화 |
| 테스트 종료 시 Windows SQLite 파일 잠금 | 실제 테스트 실패 로그 확인 | 백엔드 종료를 기다린 뒤 임시 DB 삭제 |

## 검증 계층

1. **응답 검증**: 브라우저 네트워크와 NEXON Open API 원본 응답 확인
2. **DB 검증**: 활성 스냅샷, 집계 수, 선발 슬롯과 이력 조회
3. **단위·통합 테스트**: 포메이션, 신선도, 가격, 스쿼드 메이커, 커뮤니티 권한
4. **빌드 검증**: 실제 배포 번들 생성
5. **시각 검증**: 코덱스 내 브라우저의 데스크톱·모바일 캡처
6. **배포 검증**: 새 서버 헬스체크 후 연결 전환

## AI-Native 역량으로 보여주는 것

- 불명확한 외부 시스템을 실제 증거로 해석하는 능력
- AI가 빠르게 만든 결과를 그대로 신뢰하지 않고 검증 장치를 만드는 능력
- 데이터 수집, DB, API, UI, 인증과 배포를 하나의 제품으로 연결하는 능력
- 오류와 사용자 피드백을 테스트와 규칙으로 전환해 다음 작업의 품질을 높이는 능력
